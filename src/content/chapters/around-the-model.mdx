When you use an AI product, you're rarely talking to one model. Behind the scenes there is often a small team, each member doing what it's best and cheapest at:

<Note title="Like a hospital">
The senior doctor (a large frontier model) handles the hard, open-ended cases. A triage nurse (a decision model) makes quick, narrow calls: urgent or not, which department. This nurse is new and still unproven, so check its calls. Lab technicians (small models) run routine jobs fast and cheaply. And the hospital's procedures (plain software, the harness) decide who is allowed to do what, and keep records.
</Note>

- **Large frontier models** do the open-ended thinking: understanding the task, planning, writing code.
- **<Term k="slm">Small language models</Term>** are the same kind of model made much smaller. They're fast, cheap, private when run on your own device, and can run on a laptop or phone, but they know less and are weaker at long reasoning. They're good for summarising, sorting and extracting.
- **<Term k="decision">Decision models</Term>** don't write text at all. You ask a narrow question with fixed answers ("allow, ask a human, or block?") and get back a probability for each option, in tens to hundreds of milliseconds. The category is new: <Claim id="jev-release" />. AWS (Strands Decider) and Cloudflare (Clef) followed with open versions on 1 October.
- **The <Term k="harness">harness</Term>** is ordinary software: the loop that passes messages, runs tools, enforces permissions and keeps the conversation. Agent frameworks such as the Strands Agents SDK live here.

## Try it: a safety gate for an AI's actions

An AI agent proposes a command. A decision model scores how risky it is, and plain, auditable code applies the rule. The model supplies a judgement; the policy stays in code you can read.

<Note title="Measure before you trust it" kind="warn">
A fast, confident number is not the same as a correct one. <Claim id="decision-imitation" cap />, and <Claim id="jev-routing" />. A gate built on a decision model is still probabilistic.
</Note>

<Engineer title="Decision models as a category">
A decision model is usually an ordinary pretrained transformer with a different last layer. The unembedding layer, which scores every token in a vocabulary of typically 130k to 250k entries, is replaced by a small scoring head that scores only *your* options, in a single forward pass. The body is often lightly fine-tuned as well.

<DecisionHeads />

The idea isn't new: InstructGPT's reward model (2022) also started from a language model with its final unembedding layer removed. The body keeps everything it learned about language, but the model no longer writes text.

The current models differ in the details. Strands Decider puts a pointer head on a Qwen3.5-2B body and fine-tunes it with rank-16 LoRA, a cheap method that trains a few extra weights. Clef freezes a Qwen backbone and trains a routing head with rank-256 LoRA. Laya uses a ModernBERT encoder with two added layers. Jev's design is not public. (The Strands project also makes the Strands Agents SDK below, which is why the names blur.)

<DecisionTable />

**Benchmarks in a two-month-old category:** <Claim id="decider-bench" cap />. <Claim id="clef" cap />. The makers' numbers are self-reported, and the first independent tests, mostly of Jev, are small and mixed, so measure on your own decisions.

**Harnesses and MCP.** <Claim id="strands-sdk" cap />. Harnesses run tools, manage context and retries, and increasingly connect to tool servers over <Term k="mcp">MCP</Term>. The common deployment pattern is a <Term k="cascade">cascade</Term>: a cheap model or decision model handles everything first, acts on confident answers, and passes the uncertain rest to a bigger model.

**Small models in practice.** They usually have 0.5 to 15 billion parameters, become capable through <Term k="distill">distillation</Term>, and run locally thanks to <Term k="quant">quantisation</Term>, which stores each weight in fewer bits. Typical jobs: summarising a 50k-token log before it reaches the expensive model, extraction, classification, and on-device features for data that must not leave the machine.
</Engineer>
