At the end of the stack, the model has a score for every possible next token. Those scores become probabilities: "connection" 30%, "request" 22%, "traffic" 18%, and so on down to "banana" at almost nothing. Then one token is **picked at random, weighted by those probabilities**: a weighted dice roll. The chosen token is added to the text, and the whole process runs again for the next one.

That's it. Every answer you have ever received from a chatbot was written this way, one piece at a time. It explains several things you've probably noticed:

- **The same question gives different answers,** because the dice roll differs each time, and because providers update models and hidden instructions.
- **Answers stream in word by word,** because that is literally how they are produced.
- **Long answers take longer,** because every token needs another full pass (one trip through all the layers) through the model.

Two settings shape the dice roll. <Term k="temperature">Temperature</Term> makes the model more predictable (low) or more adventurous (high). <Term k="topp">Top-p</Term> throws away the many very unlikely options before rolling. Move the sliders, then sample a few hundred times:

## Why "thinking" models are slower

Newer <Term k="reasoning">reasoning models</Term> first write out a long draft, often hidden or summarised (working through the problem, checking themselves), and only then write the answer you see. Those thinking tokens are generated the same way, one at a time, which is why they take longer and cost more. In return, answers to hard problems usually get much better, though on some tasks longer thinking doesn't help or even hurts. This is called <Term k="ttc">test-time compute</Term>: paying for quality when the question is asked rather than when the model was trained.

<Note title="Why “temperature 0” still isn't perfectly repeatable" kind="key">
Even when the model always takes the most likely token, your request is processed together with other people's, and the size of that batch subtly changes the arithmetic. Occasionally that tips a close call the other way. Deterministic in theory, very nearly in practice.
</Note>

<Engineer title="Softmax, KV cache, pricing and decoding tricks">
<Term k="softmax">Softmax</Term> exponentiates the <Term k="logits">logits</Term> divided by temperature and normalises them. Below 1 the gaps between logits grow (sharper); above 1 they shrink (flatter). <Term k="topp">Top-p</Term> keeps the smallest set of tokens whose probabilities reach p, renormalises and samples.

**KV cache.** The second token doesn't recompute the first. Every earlier token's keys and values stay in a <Term k="kv">KV cache</Term>, so each new token runs one pass of attention against it. The cache grows linearly with context and is often the real memory bottleneck.

**Prefill vs decode, and why output costs more.** Reading your prompt (<Term k="prefill">prefill</Term>) processes all tokens in parallel and keeps the GPU compute-bound. Writing (decode) produces one token per pass and streams the weights from memory each time, so it is bandwidth-bound. That's why output tokens cost several times more than input tokens, and why "time to first token" and "tokens per second" are separate numbers.

**Prompt caching.** A coding agent resends the whole transcript every step. Providers keep the KV cache for a recently seen prefix (<Term k="pcache">prompt caching</Term>), so the system prompt, tools and earlier turns aren't recomputed, and cached input is billed at a fraction of the price. Change something early in the context and everything after it must be recomputed.

**Speed and validity tricks.** <Term k="specdec">Speculative decoding</Term>: a small draft model guesses several tokens and the big model verifies them in one parallel pass; the output distribution is unchanged. <Term k="constrained">Constrained decoding</Term>: tokens that would break a JSON schema or grammar are masked out before sampling, which is how *strict* structured-output and tool modes guarantee valid JSON. Without strict mode, parsing usually works but isn't guaranteed.

**Non-determinism at temperature 0.** Floating-point addition isn't associative, but a single forward pass is actually run-to-run deterministic. The main culprit is that common kernels aren't *batch-invariant*: their reduction order depends on batch size, which depends on other users' traffic. Batch-invariant kernels fix it at some speed cost.
</Engineer>
