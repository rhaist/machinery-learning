At the end of the stack, the model has a score for every possible next token. Those scores become probabilities: in a small open model, "connection" gets about 5%, "traffic" and "request" about 3% each, and so on through tens of thousands of tokens, down to "banana" at almost nothing. Then one token is **picked at random, weighted by those probabilities**: a weighted dice roll. The chosen token is added to the text, and the whole process runs again for the next one.

Every answer you have ever received from a chatbot was written this way, one piece at a time. That explains several things you've probably noticed:

- The same question gives different answers, because the dice roll differs each time, and because providers update models and hidden instructions.
- Answers stream in word by word, because that is literally how they are produced.
- Long answers take longer, because every token needs another full pass through all the layers.

Two settings shape the dice roll. <Term k="temperature">Temperature</Term> makes the model more predictable (low) or more adventurous (high). <Term k="topp">Top-p</Term> throws away the many very unlikely options before rolling. Move the sliders, then sample a few hundred times:

## Why "thinking" models are slower

Newer <Term k="reasoning">reasoning models</Term> first write out a long draft, often hidden or summarised (working through the problem, checking themselves), and only then write the answer you see. Those thinking tokens are generated the same way, one at a time, which is why they take longer and cost more. In return, answers to hard problems usually get much better, though on some tasks longer thinking doesn't help or even hurts. This is called <Term k="ttc">test-time compute</Term>: paying for quality when the question is asked rather than when the model was trained.

<Note title="Why 'temperature 0' still isn't perfectly repeatable" kind="key">
Even when the model always takes the most likely token, your request is processed together with other people's, and the size of that batch subtly changes the arithmetic. Occasionally that tips a close call the other way.
</Note>

<Note title="Security lens" kind="warn">
Sampling produces fluent, plausible text, and a plausible name isn't necessarily a real one. That includes the names of software packages: <Claim id="pkg-hallucination" />. Attackers register the invented names and wait. [Poisoned ingredients](/learn/supply-chain/) in Part 3 covers this "slopsquatting" and how to defend against it.
</Note>

<Engineer title="Softmax, KV cache, pricing and decoding tricks">
The model's raw output is a list of scores, the <Term k="logits">logits</Term>. <Term k="softmax">Softmax</Term> turns them into probabilities: divide each score by the temperature, raise e to that power, and divide by the total. A temperature below 1 stretches the gaps between scores, so the top choice dominates; above 1 it flattens them. <Term k="topp">Top-p</Term> then keeps the smallest set of top tokens whose probabilities add up to p, rescales them, and samples.

**The KV cache.** Generating token 500 doesn't recompute tokens 1 to 499. Each token's keys and values, from every layer, are stored in the <Term k="kv">KV cache</Term>, so a new token only computes its own row and compares its query with the stored keys. Serving systems manage that memory in fixed-size pages, like an operating system's virtual memory, to fit more conversations on one GPU ([PagedAttention, Kwon et al., 2023](https://arxiv.org/abs/2309.06180)). **Why output costs more than input.** Reading your prompt, the <Term k="prefill">prefill</Term>, processes all its tokens in parallel, and the GPU spends its time calculating, which is what it is best at. Writing, the decode phase, produces one token per pass, and each pass has to stream all the weights from memory for that single token, so memory bandwidth is the limit. That is why output tokens cost several times more than input tokens, and why "time to first token" and "tokens per second" are separate numbers.

**Prompt caching.** A coding agent resends the whole transcript at every step. Providers keep the KV cache of a recently seen prefix (<Term k="pcache">prompt caching</Term>), so the system prompt, the tools and earlier turns aren't recomputed, and cached input is billed at a fraction of the price. The cache only matches an identical prefix: change something early in the context and everything after it is recomputed.

**Sampling more than once.** Asking for several answers and taking the most common one improves accuracy on reasoning tasks ([self-consistency, Wang et al., 2022](https://arxiv.org/abs/2203.11171)). Many "thinking harder" modes build on that idea.

**Faster and stricter decoding.** In <Term k="specdec">speculative decoding</Term>, a small draft model guesses several tokens and the big model checks them all in one parallel pass; the output follows the same distribution as without it. In <Term k="constrained">constrained decoding</Term>, tokens that would break a JSON schema or grammar are masked out before sampling. That is how *strict* structured-output and tool modes guarantee valid JSON. Without strict mode, parsing usually works but isn't guaranteed.

**Why temperature 0 still varies.** A single forward pass on its own is deterministic. The variation comes from batching: common GPU kernels add numbers in an order that depends on the batch size, which depends on how many other people's requests run alongside yours, and floating-point addition gives slightly different results in a different order. Batch-invariant kernels fix this at some cost in speed.
</Engineer>
