The last chapter showed that an agent is a model asked again and again, with the whole transcript each time. That makes one question decisive: what exactly is in that transcript? The model can't look anything up on its own. Everything it knows about your task, your files and your past conversations is text that the harness chose to put in front of it.

<Note title="The desk and the clerk">
Think of the context as a desk and the harness as a clerk. The clerk decides which papers go on the desk: the job description, the tool manuals, the latest results. The desk has a fixed size. When it's full, the clerk has to summarise old papers onto one sheet, or file them away and fetch them again when needed. The model only ever reads what's on the desk.
</Note>

## A desk with limits

The desk has grown fast. <Claim id="claude-1m" cap />, roughly the length of several novels. But a bigger desk doesn't mean everything on it gets read well. <Claim id="lost-in-middle" cap />. The [strengths and limits chapter](/learn/strengths-and-limits/) explains why. For agents the practical lesson is that the context is a budget to spend carefully, not a bin to fill.

Choosing what goes on the desk at each step now has a name, <Term k="ctxeng">context engineering</Term>, and it is most of what separates a good harness from a bad one. When the desk fills up anyway, the harness falls back on <Term k="compaction">compaction</Term>: it summarises the conversation so far and starts again from the summary. Try it:

<ContextDesk />

Summaries keep the gist and drop the details nobody flagged as important, which is exactly the kind of detail that matters three hours into a task. That's why good harnesses combine compaction with other tricks: clearing old tool results that are no longer needed, having the agent write key facts to a notes file, and loading files only when they're needed instead of up front.

## What "memory" really is

The model itself remembers nothing between calls. Its weights are frozen. What products call memory is a harness feature: it writes text somewhere, a list of saved facts or an index of old chats, and pastes the relevant parts back into the context later. <Claim id="chatgpt-memory" cap />.

It works less well than the name suggests. <Claim id="longmemeval" cap />. Memories also go stale: a fact saved in March may be wrong in November, and the model can't tell. Retrieval-based search over documents and memory end the same way: as text on the desk, subject to the same limits.

## How tools and know-how plug in

Agents need tools and data to work with. Instead of every product wiring up every service by hand, a few shared formats have emerged:

- **MCP** (Model Context Protocol) is a standard plug for tools and data: a mail server, a database or a ticketing system describes its tools once, and any agent that speaks MCP can use them.
- **Instruction files** such as AGENTS.md are a README for agents: the harness pastes them into the context at the start of a session.
- **<Term k="skill">Skills</Term>** package know-how. <Claim id="skills" cap />. The harness loads a skill only when a task calls for it, which keeps the desk clear.

All three are ways of getting text into the context: tool descriptions, instructions, results. That text steers the agent. It's also why the same model can do very differently in different products. <Claim id="harness-matters" cap />. A benchmark score belongs to a model *and* its harness, tools and settings, never to the model alone.

<Note title="Security note: where the agent's code runs" kind="warn">
Everything that enters the context can carry instructions: a tool description, a file, a web page, even a stored memory. <Claim id="spaiware-fix" cap />. Treat skills, instruction files and MCP servers like code from a stranger, as [Giving an AI the keys](/learn/agents-permissions/) explains.

<Engineer title="Building the context, and choosing the sandbox">
The context is assembled fresh for every call, so every design choice in a harness is a choice about tokens.

**Keep the prefix stable.** Caching only applies to an identical beginning, so put stable content first (system prompt, tool definitions in a fixed order, instruction files) and append everything else. Removing or reordering tools mid-run invalidates the cache; production harnesses mask tools they want to hide instead of deleting them.

**Compact deliberately.** Clear stale tool results first, the cheapest win. Then summarise, with an instruction to keep decisions, file paths, open problems and failed approaches. Pair it with a notes file the agent maintains and the harness reloads, so critical facts don't depend on the summary. Watch for loops where a context refills straight after compaction.

**Isolate subtasks.** A sub-agent with a clean context can read a hundred files and return a one-paragraph answer. It costs more tokens overall but keeps the main context focused.

**Treat memory as data with provenance.** Record where each memory came from and when. Let users see and delete it, and don't let untrusted content write to it without a check.

**Choose the sandbox by threat, not by habit.** OS-level sandboxes (Seatbelt, bubblewrap, Landlock with seccomp) are fine against an agent that makes mistakes on your own machine, provided they cover every tool, including file tools and MCP servers, and the unsandboxed escape hatch is disabled. Containers share the host kernel; treat them as packaging, not a security boundary, for untrusted code. For code from untrusted input or from many users, use gVisor or a microVM per session, ideally on hosts that run nothing else.

**The network and the credentials are the real perimeter.** Route all traffic through a proxy outside the sandbox with a default-deny allowlist, keep secrets out of the sandbox (inject them at the proxy or use a credential broker), give each agent its own short-lived identity, and log every request. Allowed services are attack surface too: a package cache or internal API the sandbox may reach is where escapes have actually happened.
