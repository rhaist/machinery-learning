Before a model can do anything with your text, the text gets chopped into pieces called <Term k="token">tokens</Term>. A token is usually a word or a chunk of a word. Common words like "the" or "firewall" are one token each. Rare or long words get split into several pieces. The model works with <Claim id="vocab-size" />, and every piece has a number.

<Note title="Like Lego bricks">
Imagine a box of Lego with a few hundred thousand brick types. Common words (with the space in front of them) have their own custom brick. Unusual words have to be built from several smaller, generic bricks. The model only ever sees brick numbers, never the letters printed on them.
</Note>

Try it. Type a sentence and watch it split. Then try "Strawberry", a long German word, or some code.

## Why this matters to you

- **Limits and prices are counted in tokens** (how much you can paste in, how long the answer can be), not words. In English, 1,000 tokens is roughly 750 words. Other languages, German included, usually need more tokens for the same content.
- **Letter-level tasks can be surprisingly hard.** "How many r's are in strawberry?" used to trip models up, because the model may see chunks like `str` + `aw` + `berry`, or the whole word as one token, not ten letters, so counting means recalling how each chunk is spelled. (The exact split depends on the tokenizer, and research suggests counting itself is also a weak spot.)
- **Strange input still works.** There's never an "unknown word": anything can be broken down into small enough pieces. It just takes more tokens, so it costs more and fills up the model's working memory faster.

## From pieces to meaning

A number like 892 means nothing by itself. So each token number is translated into a long list of numbers, thousands of them, that act like coordinates on a map of meaning. Imagine a map with thousands of directions instead of two; the picture below squashes it flat. Training arranges this map so that related words end up near each other, and some relationships become *roughly* consistent directions. The step from "king" to "queen" points roughly the same way as from "man" to "woman". That was first shown in older word-embedding models, and it's only approximately true inside LLMs.

<Note title="Security lens" kind="warn">
A model reads tokens, while many filters read words. A blocklist that looks for a phrase can miss it when it's split with spaces, written in another language or encoded, yet the model may still understand it perfectly. That's one reason filtering text before it reaches a model is a weak defence, as [Prompt injection](/learn/prompt-injection/) in Part 3 explains.
</Note>

<Engineer title="Tokenizers and embedding tables">
A <Term k="tokenizer">tokenizer</Term> is a fixed lookup step in front of the model. It turns text into integer IDs, and IDs back into text. It is built before the model is trained and rarely changes afterwards; adding tokens later means resizing the model's tables.

Most tokenizers today use byte-level BPE (byte-pair encoding). The vocabulary starts with the 256 possible byte values. Then the most frequent neighbouring pair in a large text sample is merged into a new token, again and again, until the vocabulary reaches its target size. Because every single byte stays in the vocabulary, any input can be encoded; the worst case is one token per byte. Watch it learn on a tiny corpus:

<BpeMerge />

The merges are recorded in order, and encoding new text replays them in the same order. Frequent words end up as one token, while rare words fall apart into the pieces the merges happened to produce. That is why "newest" becomes one token here but an unseen word like "lowest" would be "low" + "est".

Each token ID then selects one row of the model's first weight matrix, the <Term k="embedding">embedding</Term> table. That row is the token's vector: 4,000 to 16,000 numbers in large models, 1,000 to 3,000 in small ones. The width stays the same through the whole model. Every later layer reads and writes vectors of exactly that size, along what engineers call the <Term k="residual">residual stream</Term>.

Vocabulary size is a trade-off. A bigger vocabulary makes text shorter, so each prompt needs fewer tokens and fewer passes. But the embedding table grows with it: 200,000 tokens × 8,192 numbers is 1.6 billion parameters, and the unembedding matrix at the output is the same size. Small models often reuse one matrix for both jobs (tied embeddings) to save that space.

The tokenizer explains some cost and quality differences you'll meet:

- Code is cheap if the tokenizer saw plenty of it, because common indentation and keywords get their own tokens.
- German costs more: a compound like "Datenschutzgrundverordnung" splits into many pieces.
- Some tokenizers chunk numbers into groups of up to three digits ("12345" becomes "123" + "45" in GPT-4o's and Llama 3's), which makes arithmetic harder to learn. Others, such as Llama 2 and Gemma, split numbers into single digits.

In computer-science terms, the tokenizer is a deterministic compression codec, and the embedding table is an array of vectors indexed by token ID.
</Engineer>
